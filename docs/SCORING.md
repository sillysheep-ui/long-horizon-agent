# 评分口径

这份文档定义“一次评测到底报什么数、这些数怎么算、哪些数不能对外说”。
代码以 `evaluation/product_checks.py` 为准；口径变更必须先改这里。

## 一句话

对外只报 **可交付率**、**硬约束全过率**、**样本量与区间**；
综合分只在内部做版本排序；裁判未校准前，rubric 不进对外主数字。

## 两层判分

1. **确定性检查**：`product/constraints/sets/v1.json`，当前 20 条（v1.3.0）。
   每条是布尔值，判定依据是行程数据与证据，不调模型。
   条件不足（例如没有营业时间数据）的检查记为 unknown 并跳过，**不计入分母**，报告里也不出现。
2. **LLM 裁判 rubric**：`evaluation/product_judge.py`，10 条二值项，汇总为 0–1。
   每条都有“通过/不通过”的明确判据；裁判只判内容，不判结构。

## 指标定义

| 指标 | 定义 | 用途 |
|---|---|---|
| `hard_pass_rate` | 通过的检查数 / 适用检查数（逐条） | 诊断 |
| `checks_macro` | 各检查通过率的平均（每条权重相同） | 诊断 |
| `all_checks_passed` | 所有适用检查都为真 | **对外主指标**（全过率/可交付率） |
| `deliverable` | 全过 + rubric ≥ 0.7 + 无编造（裁判开启时） | **对外主指标** |
| `score`（v1） | 0.6×hard + 0.4×rubric − 0.2×编造 | 历史对比，不再新增引用 |
| `score_signal`（v2） | 0.6×signal + 0.4×rubric − 0.2×编造；门槛失败封顶 0.2 | 内部排序 |
| `pass@k` / `pass^k` | k 次采样至少一次通过 / 全部通过 | 稳定性 |

- `signal` = 去掉门槛检查后的检查集；门槛检查为 `GATE_CHECKS = {complete, day_count, evidence_ok, unique_titles}`
  （`evaluation/product_checks.py`）。
- 门槛只做“能不能交付”的判定，不重复计入内容分。
- 有裁判时，编造标记来自裁判；无裁判时用 `no_fabricated_cost` 代替，并在报告里注明。

## 为什么从 v1 改到 v2

用 110 条历史基线做过离线重算：

- 只按结构打分时 **92% 的用例满分**，5 项检查 100%，没有区分度；
- 代码判编造 **2%**，裁判判编造 **23.8%**，两者口径不一致；
- 编造组在 v1 下仍得 **0.699**，正常组 0.96，差距不够。

v2 重算后：均值 0.898 → 0.803，标准差 0.122 → **0.260**，编造组封顶 **0.35**。
所以对外不再报综合分，内部用 signal 排序。

## 对外 / 对内

**可以对外说**

- 可交付率（`deliverable`）与全过率（`all_checks_passed`），带样本数和 95% 区间；
- `pass@k` / `pass^k`；
- 失败类型分布（例如 opening_hours 占多少）；
- 延迟（均值/分位）。

**只在内部用**

- `score_signal` 的绝对值与排名；
- 单条 rubric 分数（未校准）；
- 与旧版本的配对差值（要带 bootstrap 区间，见 `evaluation/compare.py`）。

**不要对外说**

- “综合分 0.9”这类没有上下文的单一数字；
- 把沙盒成绩和联网成绩混在一起的平均值；
- 与 ChinaTravel 榜单的分数比较（评价单元与约束集不同）。

## 必须标注的上下文

任何一次报告至少写清：suite、pool（sandbox/live）、trials、judge 模型、约束集版本、
沙盒数据版本、日期、延迟。缺一项，这个数字就不能跨版本比较。
